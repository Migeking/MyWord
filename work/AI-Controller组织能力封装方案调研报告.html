1. 问题定义 Problem Statement

当前困境

你已经用 solution-builder Skill 把「方案调研与撰写」的能力封装了一次，但这只是个人级的知识沉淀。当公司有多台部署了 OpenCode 的服务器、多个人员需要使用同一套 Skill 时，问题就出现了：

问题场景具体表现影响
Skill 版本不统一每台服务器各自安装各自的 Skill，本地修改无法同步到其他机器团队输出质量参差不齐
公司模板分散历史方案模板在各人电脑上，AI 调用时无法找到最新版本方案内容不一致
人员变动风险老员工离职带走经验，AI 能力随之降级知识断层
新增设备/场景新来一个 PLC 型号，全员都要重新配 Skill效率低下
能力无法审计谁的方案用了什么模板/规则，难以追溯合规风险
核心矛盾：Skill 是文件层面的能力封装，但公司层面的能力需要高于个人、持续更新、可分发复用的机制。这不只是「安装一个 Skill」，而是一个组织知识管理的问题。
两个层次的能力封装
个人级封装
  • Skill 文件放在本地 ~/.qclaw/skills/
  • 单用户使用，无需同步
  • 更新靠手工替换文件
  • 案例：solution-builder V1.0
组织级封装
  • Skill 存放于共享位置（NAS/Git/腾讯文档）
  • 全公司统一版本，自动同步
  • 有版本管理与权限控制
  • 案例：公司级 Skill 同步方案

3. 方案对比 Approaches Comparison

方案 A：腾讯文档共享（当前方案）
优势
  • 无需额外部署
  • 天然多端同步
  • 权限管理成熟
  • 国内访问快
劣势
  • Skill 文件分散
  • 无法直接执行脚本
  • 多人编辑冲突
  • 无分支版本管理
适用：小团队（<5人），无编程能力，纯文档管理
结论：可用但不足以支撑组织能力，建议作为「文档层」而非 Skill 层
方案 B：Git 仓库（GitHub/Gitee）
优势
  • 分支版本管理完善
  • 可执行脚本一起管理
  • 多人协作规范（PR/Review）
  • Skill 完整分发
  • CI/CD 可自动化更新
劣势
  • 需要 Git 基础（团队有门槛）
  • 国内访问 GitHub 不稳定
  • 更新需要 pull 操作，非自动
适用：技术团队（懂 Git），需要 AI 编程能力的团队
结论：强烈推荐作为 Skill 的分发层。文档层用腾讯文档，代码层用 Git
方案 C：内部 SkillHub 私服
优势
  • 原生 Skill 管理体验
  • 安装即用（openclaw skill install）
  • 可上传自定义 Skill
  • 版本控制（类似 npm）
  • 可设置私有/组织可见性
劣势
  • 需要维护私服节点
  • 国内服务器需要穿透
  • 当前 openclaw skill 同步机制不完善
适用：有运维能力，中大型团队，对 Skill 分发有高要求
结论：长期最优解，短期需要先搭建 Git 做内容管理，再迁移到 SkillHub
方案 D：共享磁盘（NAS/文件服务器）
优势
  • 零技术门槛
  • 直接拖拽更新
  • 无网络依赖（内网访问）
  • 适合离线环境
劣势
  • 无版本管理（覆盖更新）
  • 无法追踪修改历史
  • 路径依赖（每个人的路径可能不同）
  • 并发冲突
适用：纯内网环境，无 IT 能力，完全不懂 Git 的团队
结论：仅适合创始阶段临时使用，长期必须迁移到有版本管理的方案
方案 E：知识库平台（Confluence/飞书知识库）
优势
  • 文档管理成熟
  • 权限控制细粒度
  • 搜索能力强
  • 天然协作
  • 可与 AI 搜索集成
劣势
  • 无法封装成 Skill（无法被 openclaw 引用）
  • 只能管文档，不能管脚本
  • AI 使用时需要手动复制粘贴
适用：大公司已有知识库平台，把知识库作为「参考文档层」，Skill 作为「执行层」
结论：不能替代 Skill，但可作为蒸馏前的知识采集层
综合建议：推荐「方案 B（Git）+ 方案 A（腾讯文档）组合」作为主要落地路径：
Git 管理 Skill 代码（含 SKILL.md + references/ + scripts/），腾讯文档管理方案模板（让非技术人员也能浏览和更新参考文档）。
长期目标是迁移到 方案 C（SkillHub 私服）做统一的 Skill 分发管理。

OpenClaw 已有能力盘点
能力描述对组织能力封装的价值

推荐架构：三层组织能力体系
第一层：知识层（腾讯文档 / 共享磁盘） ├── 原始模板（Word/腾讯文档模板） ├── 历史方案库（客户案例归档） └── 产品手册（设备规格/型号表） | 蒸馏工序（收集整理融合） 第二层：Skill 层（Git 仓库管理） ├── SKILL.md <- 主入口路由 ├── references/ <- 标准化模板（提炼后的） ├── scripts/ <- BOM计算器等脚本 └── docs/ <- 使用手册/更新日志 | openclaw skill install / git pull 第三层：执行层（全员 AI 工具） ├── 方案人员本地 AI <- AI 按 Skill 输出 ├── OpenCode 服务器 <- 运行 Agent 执行任务 └── 公司知识库 <- AI 调研时的参考来源 | 反馈环：使用反馈 -> 更新 Skill -> 重新分发 （版本号递增，Git 记录历史）
三层各司其职：
知识层：原始资料，非结构化，人可读
Skill 层：蒸馏后的能力封装，AI 直接调用执行
执行层：AI 实际产生输出的地方

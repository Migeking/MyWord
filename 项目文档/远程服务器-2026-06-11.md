## 3. SSH 自动化关键技术（**强烈建议存档**）

### 3.1 Windows 端自动填密码

原生 `ssh.exe` 不支持 `-pw`。用 **`SSH_ASKPASS` 机制**：

```powershell
# 1. 写临时 .cmd (注意: ASCII 编码，避免 BOM)
$tmp = Join-Path $env:TEMP "askpass_$PID.cmd"
[System.IO.File]::WriteAllText($tmp, "@echo off`r`necho <PASSWORD>", [System.Text.ASCIIEncoding]::new())

# 2. 设环境变量
$env:SSH_ASKPASS = $tmp
$env:SSH_ASKPASS_REQUIRE = 'force'
$env:DISPLAY = ':0'   # OpenSSH 必填, 不然不会走 askpass

# 3. 用 <nul 重定向 stdin, 触发 askpass (stdin 非 TTY 才走 askpass)
cmd /c 'ssh -T -o StrictHostKeyChecking=no -o UserKnownHostsFile=NUL root@HOST "REMOTE_CMD" <nul'

# 4. 清理
Remove-Item $tmp -Force
$env:SSH_ASKPASS = $null
$env:SSH_ASKPASS_REQUIRE = $null
```

### 3.2 PowerShell + cmd 双层引号陷阱

- `cmd /c` 会把外层双引号当字符串边界
- 内层 bash 命令必须用**单引号**包字符串，否则 cmd 抢走 `|` `>` `<` 重定向
- 远程命令里的内层 `bash -c '...'` 同样只用单引号
- 标准模板:
  ```powershell
  $cmdLine = 'ssh -T -o ... root@HOST "' + $remoteCmd + '" <nul'
  ```

### 3.3 远程脚本传递（避免在 SSH 命令行塞长脚本）

- 用 **base64 编码**后塞进命令: `echo '<b64>' | base64 -d | bash`
- 整段命令再用双引号包住交给 cmd
- 200.32 上确认有 `/usr/bin/base64` (coreutils 8.30)

### 3.4 跳板链路中的 askpass 复用

- 第二段 SSH 也要 askpass，所以脚本里要 **重新创建** `/tmp/ap.sh` 并 export `SSH_ASKPASS` / `SSH_ASKPASS_REQUIRE=force` / `DISPLAY=:0`
- 第二段 ssh 命令要加 `< /dev/null` 让其 stdin 非 TTY

## 4. 102.30 真实状态（**与初步判断不同**）

### 4.1 docker 实际在跑（更正"未安装"结论）

| 项 | 状态 |
|---|---|
| `rpm -q docker` | ❌ `package nginx is not installed` (指 nginx，docker 命令确实没装 rpm 包) |
| `dockerd` 进程 | ✅ PID 2508, 来自 `/usr/bin/dockerd --data-root=/home/docker/docker -H tcp://0.0.0.0:2375 ...` |
| `docker` CLI 在 root PATH | ❌ 没有 |
| 容器实际在跑 | ✅ 多个，UID 10000 的 nginx 进程是**容器内**的 |

**结论**: 102.30 是无 RPM 包、由二进制/脚本直接安装的 docker 环境。CLI 缺失导致 `which docker` / `docker ps` 都失败。修复方式：把 `/usr/bin/docker` 加到 PATH，或建软链到 `/usr/local/bin`。

### 4.2 nginx 真相

- 主机**无**传统 nginx 安装（`/etc/nginx/` 不存在）
- nginx 进程跑在**容器里**（PID 4944, 5508, 6228, 6230, 6233）
- 父进程是 `containerd-shim-runc-v2 -namespace moby -id ...`，确认是标准 Docker 容器
- 容器内 UID 10000 (非 root)，cwd = `/`，mount 是 overlay2（数据根 `/home/docker/docker/overlay2/...`）
- 主机端口 80 没人监听 — 容器内 nginx 要暴露 80 需要走 docker-proxy，目前没看到 :80 的 docker-proxy

## 9. 紧急事件: 1Panel 端口不通 (cfw-tap 驱动拦截)

**触发时间**: 2026-06-11 晚上装好 1Panel 之后
**现象**: 200.32 上 1Panel 一切正常（本地三个 IP curl 都 200），但从 Windows `192.168.200.15 → 192.168.200.32:10086` **死活不通**（TCP SYN 直接丢）。奇怪的是同一个 200.32 的 **22 端口（SSH）完全正常**。

### 9.1 排查路径

| 排除项 | 证据 | 结论 |
|---|---|---|
| 1Panel 自身问题 | 200.32 本地 `curl 127.0.0.1:10086` = 200, `curl 192.168.200.32:10086` = 200, 重启后仍 200 | ❌ 不是 |
| 200.32 防火墙 | `iptables INPUT` policy ACCEPT, 没拦 10086, nftables 没 DROP | ❌ 不是 |
| 200.32 路由 | `ip route get 192.168.200.15` 走 edge0, ARP 表 200.15 REACHABLE | ❌ 不是 |
| 200.32 收包 | `tcpdump -ni any 'tcp port 10086'` 5 秒 = **0 packets** | Windows 的 SYN **根本没到 200.32** |
| Windows 防火墙 | 三个 Profile 全 `Disabled`, 219 条入站规则无 10086 相关 | ❌ 不是 |
| Windows 路由 | 200.0/24 直连在 cfw-tap 上, 最长前缀匹配会走 cfw-tap | 看起来对 |
| Clash 进程 | `clash-core-service` + `FlClashHelperService` 存在 | ⚠️ 嫌疑, 但杀完后仍不通 |

### 9.2 真相定位

杀完 Clash 进程后，**10086 仍然不通**。继续深挖发现关键证据：

```
$ Get-PnpDevice
Status FriendlyName              InstanceId
------ ------------              ----------
Error  TAP-Windows Adapter V9    ROOT\NET\0000   ← 老的, cfw-tap (Disabled)
OK     TAP-Windows Adapter V9 #2 ROOT\NET\0001   ← 新的, "以太网 4" (Up, 持有 200.15)
```

**系统里有 2 个 TAP 设备**：
- 老的 `cfw-tap` (Disabled) — 我之前一直以为 200.15 在它上面
- 新的 `以太网 4` (Up) — **真正的 200.15 宿主**（驱动 `tap0901.sys` v9.23.2, OpenVPN 项目）

且：
- `以太网 4` 持有 `192.168.200.15/24`，但**接口描述是 "TAP-Windows Adapter V9 #2"**（第二个 TAP 实例）
- TAP 驱动对特定入站端口（10086）有过滤，但允许 22 — 这就是为什么 SSH 通、10086 不通

### 9.3 ⚡ 临时解决方案: SSH 本地端口转发（30 秒搞定，100% 通用）

**核心思路**: 用通的 22 端口建立 SSH 隧道，把不通的 10086 通过隧道内部 loopback 转发到本地。

```powershell
# 在 PowerShell 里执行（一次性，会保持后台运行）
ssh -f -N -o StrictHostKeyChecking=no -o UserKnownHostsFile=NUL `
    -o ServerAliveInterval=30 -o ServerAliveCountMax=3 `
    -o ExitOnForwardFailure=yes `
    -L 10087:127.0.0.1:10086 root@192.168.200.32
# 提示输密码: <200.32 的 root 密码>
```

然后浏览器开：**http://127.0.0.1:10087/1panel**

**转发逻辑**:
```
浏览器 → 127.0.0.1:10087 (本地) 
       → SSH 22 (通的!) 
       → 200.32 内部 127.0.0.1:10086 (loopback, 不会被 TAP 驱动拦) 
       → 1Panel
```

### 9.4 这个方案的适用场景

## 11. ⚠️ PowerShell 5.1 编码坑 (踩过, 记一下)

**症状**: 用 PowerShell 写了带中文的 `.ps1` 脚本并执行，提示 `字符串缺少终止符` / `Try 语句缺少自己的 Catch 或 Finally 块` 等莫名其妙的解析错误。

**根因**: 
- Windows PowerShell 5.1 读脚本时：**有 BOM** → 当 UTF-8 读；**无 BOM** → 当系统 ANSI (中文 Windows 是 GBK) 读
- 用 `[System.Text.UTF8Encoding]::new()` 写文件 → **无 BOM**
- UTF-8 字节被 GBK 解释 → 中文乱码 → 解析器炸
- PowerShell 7+ 无此问题（默认按 UTF-8 读无 BOM 文件）

**复现**:
```powershell
# 写 no-BOM UTF-8 (中文字节是对的, 但没 BOM 头)
$content = '中文 Write-Host "按 Enter 退出"'
[System.IO.File]::WriteAllText("test.ps1", $content, (New-Object System.Text.UTF8Encoding))
# 用 PS 5.1 跑 -> 报字符串缺少终止符
```

**修法 (3 种任选)**:

```powershell
# 方法 A: 写时直接带 BOM (推荐)
$utf8Bom = New-Object System.Text.UTF8Encoding $true   # $true = emit BOM
[System.IO.File]::WriteAllText("test.ps1", $content, $utf8Bom)

# 方法 B: 写完后给已有文件补 BOM
$path = "test.ps1"
$bytes = [System.IO.File]::ReadAllBytes($path)
$new = New-Object 'byte[]' ($bytes.Length + 3)
$new[0]=0xEF; $new[1]=0xBB; $new[2]=0xBF
[Array]::Copy($bytes, 0, $new, 3, $bytes.Length)
[System.IO.File]::WriteAllBytes($path, $new)

# 方法 C: 装 PowerShell 7+ (pwsh.exe), 它默认正确读 UTF-8
# https://aka.ms/PSWindows
```

**本项目里的脚本都已补 BOM** (3 个 .ps1 文件全 ✅):
- `D:\code\MyWord\项目文档\fix-tap-driver.ps1`
- `D:\code\MyWord\项目文档\restore-tap-driver.ps1`
- `D:\code\MyWord\scripts\1panel-tunnel.ps1`

**经验**: 在中文 Windows 上写跨平台 / 跨 PS 版本的脚本，**永远带 BOM** 是最稳的。要么坚持用 PS 7+。
